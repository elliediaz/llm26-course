# 2회차 미션 데이터

2회차 미션 M2~M5에서 쓰는 데이터 모음임. 모두 이 저장소 안에 들어 있으므로 따로 내려받을 필요 없음.

| 파일 | 내용 | 규모 | 쓰는 곳 | 출처·라이선스 |
|---|---|---|---|---|
| `delivery_reviews.json` | 배달앱 리뷰 유형(맛·배달·양·포장·칭찬) | 개발 25 · 시험 50 | M5 | 직접 작성(가상), CC BY 4.0 |
| `smishing.json` | 문자 판별(정상·스미싱) | 개발 20 · 시험 40 | M5 | 직접 작성(가상), CC BY 4.0 |
| `news_ynat.json` | 뉴스 제목 분야(IT과학·경제·사회·생활문화·스포츠) | 개발 50 · 시험 100 | M5 | KLUE-YNAT 검증셋 일부, CC BY-SA 4.0 |
| `game_inquiry.json` | 게임 고객 문의 유형(결제·밸런스·버그·이벤트·제재) | 개발 18 · 시험 51 | M5 | 과정 G 도메인 데이터 일부(가상 게임), CC BY 4.0 |
| `proverbs.json` | 속담 앞부분·뒷부분 | 한국어 40 · 영어 10 | M4 | 전래 속담(퍼블릭 도메인) |
| `token_zoo.json` | 토큰 수 비교용 표본 문장 | 8종 × 2문장 | M3 | 직접 작성, CC BY 4.0 |
| `coref_sentences.json` | 지시어 문장 12 · 다의어 문장 10 | 22문장 | M2 | 직접 작성(Winograd 스키마 형식 차용), CC BY 4.0 |

영화 리뷰(NSMC)는 1회차 데이터 `data/common/nsmc/`를 그대로 씀(`--task nsmc`).

## 분류 데이터 구조(M5)

```json
{
  "name": "배달앱 리뷰 유형",
  "task": "delivery",
  "scenario": "상황 설명",
  "instruction": "기본 지시문(프롬프트 경연에서 바꾸는 부분)",
  "input_name": "리뷰", "answer_name": "유형",
  "labels": ["맛", "배달", "양", "포장", "칭찬"],
  "dev":  [{"text": "...", "label": "맛"}],
  "test": [{"text": "...", "label": "배달"}]
}
```

- `dev`(개발셋) : 프롬프트를 고치면서 몇 번이고 돌려 보는 셋. 예시(`--shots`)도 여기서 뽑음
- `test`(시험셋) : 마지막에 한 번만 돌리는 셋. 시험셋을 보며 프롬프트를 고치면 점수가 부풀려짐
- 라벨마다 개수를 맞춰 두었으므로 찍기 수준 정확도는 1 ÷ 라벨 수임

## 작성 원칙

- 실존 상호·인물·전화번호·계좌를 쓰지 않음. 스미싱 문자의 주소는 모두 예시용 도메인(`.example`)임
- 직접 작성한 문장은 실제 서비스에서 흔히 보이는 유형을 참고해 새로 쓴 것임
- 뉴스 제목은 KLUE-YNAT 검증셋(klue/klue, ynat)에서 8~40자 제목을 분야별로 무작위 추출함
  (Park et al., 2021, *KLUE: Korean Language Understanding Evaluation*, CC BY-SA 4.0). 이 파일을 고쳐 배포할 때도 같은 라이선스를 따라야 함
- 해외 클라우드(코랩·RunPod)에서 써도 문제없는 데이터만 넣음. AIHub 데이터는 넣지 않음

## 알아 둘 점
- 라벨이 애매한 문장이 조금 있음. 예를 들어 배달 리뷰의 '다른 집 음식이 왔어요'는 배달로 붙였지만 포장·주문 실수로 볼 수도 있음. 틀린 예를 볼 때 모델 탓인지 라벨 탓인지 같이 봐야 함
- 게임 문의는 G 도메인 시드에서 유형별로 뽑았고, 이벤트·제재는 문장 수가 적어 시험셋이 7~8건뿐임

## 직접 데이터 만들기

같은 구조로 JSON 파일을 하나 만들고 `python src/llm_classify.py --data <파일>`로 돌리면 됨.
라벨당 개발 5건 · 시험 10건 정도면 2회차 실습 규모로 충분 함.
